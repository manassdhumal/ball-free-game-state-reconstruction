# Step 81: Controlled Ball-Free Event Evaluation

## Research question

Do player-only possession transitions align with annotated event transitions in the available controlled Metrica data? This is annotated tracking/event validation, not SoccerNet-GSR or real-broadcast perception validation.

## Data and labels

The experiment uses Metrica Sample Game 1, frames 1-1500 (0-60 seconds at 25 FPS). The canonical event parser provides `PASS`, `BALL LOST`, `RECOVERY`, `BALL OUT`, `CHALLENGE`, and `SET PIECE` labels in this window. Only transition-compatible labels are evaluated:

- `pass_candidate` -> `PASS`
- `turnover_candidate` -> `BALL LOST` or `BALL OUT`
- `recovery_candidate` -> `RECOVERY`

The `BALL LOST`/`BALL OUT` pairing is a project evaluation mapping for a generic turnover candidate. The player-only model does not independently distinguish those two source annotation labels.

`CHALLENGE` and `SET PIECE` are retained in the source data but excluded because the player-only transition taxonomy does not claim to detect them.

## Inference/evaluation separation

Candidate events are generated by the existing ball-free possession state machine from player tracking only. Allowed inputs are player coordinates, team, identity, visibility, spatial relationships, and temporal state. Ball coordinates, event labels, future frames, and post-event information are not passed to inference. Metrica labels enter only after candidates are complete, during evaluation.

## Matching policy

Evaluation uses one-to-one greedy temporal matching. Candidate/reference pairs within the configured tolerance are sorted by absolute frame difference; each predicted event and reference event can be matched once. Duplicate predictions with the same event type and frame are removed. Unmatched predictions are false positives and unmatched references are false negatives. Tolerances are 0.20, 0.50, and 1.00 seconds, converted using the configured 25 FPS metadata.

## Metrics and protocol

The experiment uses a fixed existing inference configuration rather than tuning against event labels. It reports per-event-type and aggregate true positives, false positives, false negatives, precision, recall, F1, mean timing error, and median timing error. Because the available controlled sample is one match/window, no development/evaluation threshold split is claimed; tolerance sensitivity is reported instead. Confidence intervals are not estimated because the experiment has one match-level evaluation unit and the main purpose is transparent tolerance analysis.

Outputs are isolated under `results/step81/metrics/` and `results/step81/figures/`. The exact command is:

```text
.venv\\Scripts\\python.exe -m src.validation.step81_event_evaluation --config configs/step81_event_evaluation.yaml
```

## Limitations

This result measures controlled player-only event alignment against Metrica annotations. It does not establish broadcast-video performance, SoccerNet action-spotting performance, causal event semantics, or genuine GSR perception quality. Event timing reflects annotation and player-only transition timing, and excluded labels are not negative evidence that the system failed to detect them.
